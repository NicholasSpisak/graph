A skill for Claude Code & OpenAI Codex

A graph is a map of loops + checkpoints.

A loop and a graph are both ways to run an agent — the difference is who decides the path. For the jobs you run every week, you draw the map. The /graph skill drafts it for you: the nodes, the gates, the routes, and a brief for every agent on the map.

01

Loop vs graph: who decides the path

A loop still starts with you — you set the goal, the brief, and the bar it has to clear. What the agent owns is the path: it drafts, reads the draft back against the brief, rewrites the weak parts, and keeps circling until it clears. A graph is you drawing the steps and the routes between them ahead of time. The agent still decides how to handle each step — it just travels the routes you laid down.

The loop

The agent decides the path

turn by turn, until it clears the bar

  • You set the goal — the outcome you want
  • You set the brief — context and constraints
  • You set the bar — what good enough has to clear
  • The one thing you never wrote: the step-by-step it took
The graph

You draw the paths first

the agent fills each one in

  • Every node is a state the work can be in
  • Every checkpoint reads the result and routes it
  • Forward when it clears, back when it misses
  • The agent still solves each node its own way

The shape has a name: a state machine.

If you have built a workflow in n8n, you have already drawn one — nodes wired together, branches that fire on a condition, a step that loops until it clears. An agent graph is the same shape; the nodes hold agents doing the work instead of single API calls.

02

A map of loops and checkpoints

Some nodes run once. Others are their own loop — a critic scores each draft against a rubric and sends it back until it clears the bar. The checkpoints between them read the result and route the work. You keep laying down nodes and checkpoints until the map reliably gives you the output you want. Then you reuse it: feed it the next keyword, the next cohort, and the whole pipeline runs again. The skill drafts the map as two committed artifacts:

Artifact one

graph.md

the map · one file per graph

  • State schema — every key, one writer each
  • Nodes table — one responsibility, one output key
  • Routes — a mermaid diagram that is the map
  • Gates — JSON checks with a pass and a fail route
  • Failure map + max_steps so every run halts
Artifact two

nodes/*.md

the briefs · one file per node

  • Reads — the state keys it takes in
  • Writes — its one output key, exact shape
  • Instructions — the node is this section
  • Done-when — observable, not "when it's good"
  • Refusals — the fence around the node

The map is harness-agnostic: the same two artifacts drive Claude Code (Workflow or chained sessions), Codex CLI (chained codex exec), an n8n canvas, or a LangGraph port. State lives on disk, so any runtime — and any human — can inspect a run mid-flight.

03

When each earns its place

A loop on its own is enough for the work you only do once, where you don't know the path yet — let the agent find it. A graph earns its extra setup on anything you run every week: the content pipeline, the SEO / AEO funnel, the cohort accelerator.

Reach for a loop when

The path is unknown

  • One-off or exploratory work
  • You can state the bar but not the route
  • The overhead of a map would outweigh the job
Reach for a graph when

The job repeats

  • Validation gates the work cannot skip
  • A fixed set of routes the job can take
  • A clear failure point — the exact step it broke on

The skill opens with a loop-or-graph gate.

If the job is one-off, it tells you a loop is enough and stops — no ceremony graph for a one-step task. Its own rule 8 applies to itself: the smallest graph that makes the real control flow visible.

04

Ten rules for the topology

Each rule exists because a real failure mode punished its absence. The skill designs to all ten; when two collide, rule 8 — the smallest visible graph — wins.

One job, one key

Each node gets one clear responsibility and a unique output key. A node described with "and" is two nodes; a key with two writers is a race.

Fan out only independent work

Parallel nodes must not read each other's output. All-source joins take an explicit list of sources — the list is the contract.

Repo edits stay sequential

Unless each editing node has its own isolated worktree. Runtimes disable parallel execution for coding agents sharing one cwd — design as if yours doesn't.

Reviewers return JSON

Merged into state: approved, issues, summary. Gates route on the verdict; fix nodes repair from the issues list. Prose can't be routed on.

Approve ends, reject corrects

Approval routes to __end__. Rejection routes to a corrective node and back to the same review — never "ship it anyway", never a fresh dice-roll.

Human nodes are rare

Only for a consequential choice — spend, publish, delete — or a checkpoint the user asked for. A human node parks the run until someone shows up.

Every cycle is bounded

A finite max_steps for every topology containing a cycle, and a cap on every looping node. A bounded failure beats an unbounded bill.

The smallest visible graph

Every node earns its box: a distinct responsibility, a distinct failure mode, or a gate that needs it. Never turn a one-step task into ceremony.

Side effects after gates

Publish, spend, delete — only downstream of the gate that authorizes it. Everything upstream of a gate must be safe to re-run, because resumed runs re-execute the node from the top.

The graph passes a gate

The compiler declares the map well-formed; you declare it right — on a rendered review page, stamped by hash into the lock file. Drivers refuse an unapproved or drifted map.

Full rationale and examples ship inside the skill — references/topology-rules.md.

05

The workflow it runs for you

Describe the job and the skill does the drawing — grounded in your SOPs, your failure history, and your rubric.

Gates loop-or-graph

Will the job run again? Are there checks it must not skip? Could you sketch the route on a napkin? Mostly no → it recommends a loop and stops.

Gathers the raw material

The deliverable and its cadence, the rubric every gate scores against, the route you already run by hand (or in n8n), where past runs broke, and which choices deserve a human.

Designs the topology

Applies the ten rules: one responsibility per node, gates as JSON verdicts, rejection routed through a fix node, every cycle bounded, repo edits kept sequential, side effects after gates — and binds each node to the model it deserves: Claude on judgment and review, Codex on implementation.

Drafts the map

Writes docs/graphs/<slug>/graph.md — state schema, nodes table, mermaid routes, gates table, failure map, runtime notes — from a strict template.

Drafts the node briefs

One brief per node: reads, writes, instructions, done-when, refusals. Reviewer briefs pin the exact JSON they return; loop nodes state their internal bar and cap.

Validates and hands off

A compiler mechanically checks the map — unique output keys, both routes on every gate, targets that exist, a reachable __end__, a finite max_steps — locks it by content hash, and renders a visual review page. You approve it before anything runs; then it emits the drivers for Claude Code and Codex CLI.

06

Install & use

One command installs the skill through the Vercel npx skills CLI — it detects your agents and asks where to put it. Then describe the job you repeat and let it draw the map.

# preferred — the Vercel skills CLI
npx skills add NicholasSpisak/graph

The CLI detects which agents you have (Claude Code, Codex, and more), asks whether to install into your current project or globally, and whether to symlink for auto-updates or copy. Prefer a script? git clone the repo and run ./install.sh — see the README.

In Claude Code
/graph our weekly SEO article pipeline —
       audit, draft, score vs rubric, publish
In Codex CLI
$graph our weekly SEO article pipeline —
       audit, draft, score vs rubric, publish

It drafts the map and the briefs into docs/graphs/, validates them, and tells you how to run the graph — Claude Code Workflow, chained codex exec, or your n8n canvas. Once the map works, feed it the next cohort and the whole pipeline runs again.
